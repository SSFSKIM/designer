## Purpose

Every native pixel vitrea has ever been measured against was captured on macOS 26.5.2. Apple
shipped macOS 27 on 2026-09-14 and says the material changed underneath every app without a
recompile: stronger diffusion of complex content, a darkened edge, brighter specular highlights,
more uniform refraction, a common tighter window corner, edge-to-edge sidebars, uniform toolbars,
and a user-facing transparency slider whose default is the centre of a range from ultraclear to
fully tinted. The project's goal is the least possible gap between vitrea and Apple's material, and
from 2026-09-14 "Apple's material" is what a Mac on 27 draws. This wave moves the reference.

It does so in the order the fidelity discipline requires. First the 26.5 evidence is frozen and
proven untouched. Then Apple's 27 material is captured under new keys with every axis that can move
a pixel attested per run, including the two 27 introduces (the slider; Show Borders decoupled from
Increase Contrast). Then what 27 changed is **measured native against native**, cell by cell,
against a noise bar taken from the 27 bed's own run-to-run behaviour, and written into the ledger
before any line of vitrea moves — so the refit that follows is a response to a measurement, not to
a press release. Only then is the material refit, on the WebGPU tier with the CSS tier derived in
the same wave, under 27 profile documents, judged by bounds declared before the read, with the
holdout read once. The 26.5 documents, fixtures and rows stay as committed evidence; the 26.5
bounds keep running against the frozen 26.5 rows and the 26.5 material fingerprint stays pinned,
which together prove that nothing there moved.

What this wave does **not** do: it does not identify the abscissa (W28 §Deferred; re-runnable on
the 27 bed afterwards), it does not build the motion-metrics harness (next), and it does not
capture the slider's two ends as evidence classes unless G0 shows the slider moves the cells at all
and the user rules them in.

## Grounding Baseline (main at `6ac184c1`, 0.18.0 published)

- **The 26.5 bed.** Six profile directories, 619 fixture PNGs (164 / 164 light standard 1x / 2x,
  115 / 114 dark standard, 32 increased-contrast, 30 reduced-transparency; 277 of them inactive),
  32 background PNGs, one `manifest.json` whose `hardware` block reads macOS 26.5.2 build 25F84,
  MacOSX26.5.sdk, Xcode 26.6 17F113, Mac14,12 M2 Pro. `results/matrix.json` schema 5, 1,107 rows
  (563 light standard, 437 dark standard, 55 IC, 52 RT; probe 720, calibration 264, validation 64,
  holdout 59). `scenes.json` version 5: 168 scenes, split calibration 37 / validation 12 / holdout 20
  / recorded 8 / probe 91.
- **The appearance setting the 26.5 bed was captured under.** macOS 26 offers Liquid Glass as
  *Clear* or *Tinted* in System Settings › Appearance. No preference key for it exists in any plist
  under `~/Library/Preferences` on the capture machine (searched 2026-09-16, before the update), which
  is what a never-touched default leaves behind; the bed therefore stands at Apple's 26 default. The
  setting itself was never recorded in a manifest. **Recorded here as an inference from the absence
  of a key, not as an attestation**; the user can confirm the pane's state before updating.
- **What is coupled to 26.5.** One hard gate: `results/2026-09-11-w27-26.5-run/run-sitting.sh:50`
  refuses any `sw_vers` not `26.5*`. The Swift harness has no `#available`, reads no OS version
  except to *record* it (`Manifest.swift`), and validates the a11y, scale and scheme tokens of a
  profile key against the machine but **never the OS token** — nothing in the harness would stop a
  27 machine writing into a 26.5 directory. Profile keys are literals in `scenes.json` (six of
  them), copied verbatim into fixture directory names and manifests; the material profile documents
  are named by convention and passed by path (`--material-profile`), with three consumers that
  hard-code the 26.5 filename (`platform-web/src/dark-profile.ts`, two calibration tests). Tests
  pinning 26.5 names: `adopted-thresholds` (74 hits: floors, per-profile bounds, cell counts,
  36 `PREDICATE_EXCLUDES` entries), `scene-matrix` (16), `tuned-profiles`, `report`, `profile-key`,
  `vibrancy` (asserts the build set is exactly `Version 26.5.2 (Build 25F84)`), five more with one
  or two each; the demo's site, calibration and vite config name the two fixture directories it
  ships and `pages.yml:73` asserts the light one exists.
- **The key grammar.** `PROFILE_KEY_PATTERN` accepts `\d+\.\d+` for the OS token, so
  `apple-macos-27.0-…` parses today and a bare `27` would not. The grammar ends at the a11y token:
  it has **no slot for the slider** and its `a11yMode` enum cannot express Show Borders decoupled
  from Increase Contrast (c9a §5.134 already names both).
- **The granted bundle.** `apps/reference-apple/build/VitreaReference.app` is not in git; built by
  `build.sh` with plain `swiftc`, `-target arm64-apple-macos26.0`, MacOSX26.5.sdk, ad-hoc signed,
  bundle id `dev.vitrea.reference-apple`. Screen Recording is granted to that signature and a rebuild
  invalidates the grant until the user toggles it (README, tracker); a recorded denial suppresses
  the prompt, so a broken grant fails silently. Its ScreenCaptureKit calls are all ≤ macOS 14 APIs,
  none deprecated; deployment target 26.0 launches on 27. **It can be reused byte-for-byte**, and
  `VITREA_BUILD_OUT` builds a side bundle beside it for any experiment.
- **The scientific risk of reuse.** The bundle links the 26.5 SDK, and macOS routinely gates
  appearance changes on the linked SDK version. Apple's statement is that existing apps get the 27
  material without recompiling; if any part of it is SDK-gated, a bed captured with the granted
  bundle would be labelled 27 and draw 26-era glass. Settled by one comparison (G0).
- **What the metrics can and cannot do.** `measureCell` is native-against-web by construction;
  `ResultCellKey` requires a `WebCell`, so the result matrix cannot hold a native-against-native
  row. The primitives are image-pair generic (`ssim`, `oklabDeltaE`, `silhouetteIoU`,
  `contourDistance`); `cli/tier-delta.ts` is the precedent for a pair diff with no fixture in it;
  `src/plurality.ts` classifies byte-level run-to-run differences as noise or structural. A
  native-delta driver has to be written (G2) and its rows live beside the matrix, not in it.
- **Capture cost, from the 26.5 record.** The harness runs 9.5 s per cell. W27c's 188-cell round
  was 29.8 min per run, 3.5 h at the seven-run bar before attempt loss, 4.4 h wall in `sitting.md`.
  A full 27 bed of 624 declared cells is about 99 min per run; at seven runs ≈ 11.5 h before the
  record's 1.3–2.5× attempt-loss, so **15–29 h of unattended machine time** across passes, each
  pass one scale × one accessibility mode × one pose (about eight passes); the two accessibility
  passes need the user to flip System Settings. The 624 is the declared count; 619 were ever
  published on 26.5. Those hours are idle wall-clock during which the machine can run no browser
  suite (X7) and must stay untouched (the 45 s idle gate), so the bed costs **days of machine
  unavailability, not hours of work**; the 73 cells that had a seventeen-run bar on 26.5 are not
  re-captured at seventeen (clause 4 adopts no floor).
- **The bar the 26.5 cells were published at.** `bedProvenance` has 13 entries with run counts
  and a single `cellsSha256` each; it names cells for 91 (the frequency-settled ones), 73 cells sat
  at a seventeen-run bar (entries 0–2), 121 fixtures carry `recoveredProvenance` at one run per
  cell, and the publication events sum to 444 against 619 fixtures. A per-cell 26.5 bar is not
  derivable for most of the bed; clause 2 therefore declares one bar per pass.
- **The display.** Every profile's `display.displayName` is `가상 16:9`, a BetterDisplay virtual
  screen, and the two scales are reached by switching it between displayplacer modes 68 and 69.
  Without that third-party driver there is no 1x bed at all (four of six keys). The manifest's
  `sdk` field is read from the `VITREA_SDK` environment, which `capture.sh` derives from the
  installed SDK, not from the binary — after Xcode 27 is installed a run with the 26.5-linked
  bundle would attest `MacOSX27.sdk`.
- **The machine.** Mac14,12 (M2 Pro, Apple silicon, so 27-eligible), macOS 26.5.2, Xcode 26.6.
  Software Update offers macOS 27 build **26A428** (the same build as the 2026-09-09 RC) and macOS
  26.7. Reduce Transparency and Increase Contrast read 0 / 0 on 2026-09-16.
- **Public record of the change** (all secondary except the WWDC26 State of the Union and Apple's
  macOS page; see the research note): darkened edge, brighter speculars, stronger diffusion, more
  uniform refraction; window corners common and tighter (secondary: 20 pt from 26); sidebars
  edge-to-edge with colour; uniform toolbars on scroll; window shadows separating active from

## Design (advisory unless marked)

- **Keys.** [binding] `apple-macos-27.0-<scale>x-<scheme>-<a11y>`, the OS token equal to
  `sw_vers -productVersion` major.minor read at the run's opening. The shell gate that refused
  non-26.5 becomes a gate that refuses non-27.0 for this bed, and `materialize` refuses a manifest
  whose parsed major.minor (from `hardware.osVersion`, which reads `Version 26.5.2 (Build 25F84)`
  today, so the check parses rather than prefix-matches) and `osBuild` do not match the key and
  the declared build — the check the harness never had, added in TypeScript so the granted bundle
  is not rebuilt for it.
- **The slider.** [binding] G0 measures whether it moves the harness's cells at all, before the
  key grammar is touched. If it does not move `.glassEffect()` surfaces, the position is attested in
  the manifest as a required field read from the machine (a defaults key found by diffing before
  and after moving it, or whatever store G0 finds), and the key stays as above. If it does, the
  grammar gains a trailing token and the bed is captured at the default (centre) position only;
  the ends are evidence classes for the user to rule in or out. **If G0 finds no machine-readable
  position, the wave stops at Decision Log 2**: an attestation in this project is a read that can
  refuse (as Reduce Transparency and Increase Contrast are read in `main.swift`), and a screenshot
  of the pane cannot refuse anything; if the user rules a screenshot in, the manifest field is
  labelled an operator assertion and the ledger says so. Either way the 27 bed is captured at the
  centre, which is what a Mac shows by default.
- **Show Borders.** Off and attested in every run; not an evidence class in this wave (Deferred).
- **The native delta driver** (G2). A CLI shaped like `tier-delta.ts` over two fixture
  directories, writing `results/<dir>/native-delta.json` rows keyed `{ profileKey27, profileKey26,
  sceneId }`, with the same metric primitives the fidelity read uses and the rim-band and highlight
  reads from the 26.5 waves (W23, W24). The noise bar is taken from the 26.5 plurality record
  (run-to-run maxDelta / changedPx on the same cell) so "moved" means "moved more than 26.5 moved
  against itself".
- **The runtime default does not move** [binding — Decision Log 1]. `DEFAULT_MATERIAL_PROFILE`
  stays the 26.5 light material, because the 26.5 light document is pinned as the identity with the
  runtime default (`tuned-profiles.test.ts`, `dark-profile.ts`) and moving the default would turn
  that frozen document red with no remedy X1 allows. The 27 material ships as **patch documents**
  — the 27 light patch over the runtime default, the 27 dark difference document, the 27 receded
  endpoints — resolved through the same `withMaterialOverrides` path, each carrying its own
  `resolvedMaterialSha256`. Which document a page gets by default is then a **selection** in
  `platform-web`, which is clause 5's ruling, not a change to the default constant. A later wave
  may convert the 26.5 light document to an explicit patch and move the default, under a named
  one-time exemption recorded before it opens; this wave does not.
- **The refit** (G3) is chartered from G2's reading, not from this document: which laws moved
  (rim/edge darkening, highlight amplitude, scatter/diffusion, tone response, corner geometry) is a
  finding, and the child's acceptance names them. The mechanism precommit rule from W28 applies: no
  new operator is added to the material because a review article names an effect; an operator is
  added when the native delta shows a structure the existing profile cannot fit.
- **The default target** (clause 5) is the user's; the parent's recommendation is 27 by default
  with the 26.5 documents kept in `profiles/` as evidence and selectable through the existing
  `applyMaterialProfile` path, since every Mac that installs the update draws 27 and a page has no
  OS to follow.

## Risks & Mitigations

- **SDK-gated material** (G0 (c)); mitigated by measuring before the bed, not after.

## Surprises & Discoveries

- **On macOS 27 Apple's glass over near-black is no longer invisible, and the shape axis is how we
  found out** (2026-09-19, G2; §5.151 §4). 66 of 619 cells have one bed's silhouette under half the
  other's, 55 of them with the small one on 26.5 and over `dark-solid` (32), `impulse` (11),
  `light-solid` (6), `mid-dark-solid` (4), `hc-text` (1) and `hc-text-7` (1) — the last two were
  dropped from the first writing of this list, which summed to 53 (review closure 2026-09-19).
  The extractor calls a pixel "inside" when it differs
  from the backdrop by 0.02 linear, and on 26.5 Apple's material over those backdrops did not:
  `dark-solid__rrect-64__rest` is **52 px** of silhouette on 26.5 and **6,996 px** on 27. The
  tracker already carries this as a fault of the shape axis — and on this read it is not noise, it
  is the finding. These are the very cells the user's eye named on the W22 sheets ("glass on black
  invisible where Apple's shows an outline", §5.99), and two waves of vitrea work were fitted to a
  reference that has moved on exactly them. The procedural consequence: every silhouette-masked
  statistic on those cells is taken over a few dozen pixels, so the level and tone laws are read
  from the mask-free `bodyLevel` instead.
- **The noise bar reproduced the sitting's publication record without being asked to** (2026-09-19,
  G2; §5.151). The number of cells whose whole-cell metrics have exactly zero spread across all 21
  within-bed pairs is **505 of 624** — precisely the count of cells the plurality published
  unanimously across all seven runs (§5.150 Part B §4). One construction works on bytes and the
  other on SSIM, ΔE and edge-weighted difference, and they agree cell for cell. Nothing planned
  this; it is the strongest single check the gate has that the bar is reading the bed it thinks.
- **Three metrics have no resolution in this bed at all** (2026-09-19, G2; §5.151). Across 13,104
  within-bed pairs, `contourDistanceP95Px`, `oklabDeltaEP95` and `rimPeakDepthDeltaPx` never once
  took a non-zero value: a 95th percentile over pixels and a rounded ring index are both blind to
  the handful of pixels a re-run moves. The declared zero-spread fallback — the bed-wide minimum
  non-zero spread — is undefined there, so the rule was extended **before the first pair was read**
  to make the bar exactly zero, which is the strongest of the three levels rather than the weakest.
  The general lesson: a bar taken from a bed's own variation has a floor, and a metric can be so
  coarse that the bed's variation never reaches it.
- **A hue is not a reading until its chroma is stated** (2026-09-19, G2; §5.151 §7). `tintResponse`
  documents that its hue is meaningless at near-zero chroma, and the bed splits exactly there: 456
  of 569 cells have an interior chroma under 0.01 on both beds and a median hue "shift" of **82°**,
  while the 113 cells at chroma ≥ 0.01 read **1.0°**. Read bed-wide the row says the tint's hue
  swung 67°; read on the cells where a hue exists it says the hue did not move. The bar cannot catch
  this — the readings are real numbers and they clear it — so the condition has to come from the
  metric's own documentation, which is an argument for keeping such conditions next to the code.
- **macOS 27 does NOT couple Reduce Transparency to Increase Contrast** (2026-09-19, G1 Part B;
  §5.150 Part B §3). On 26.5 Increase Contrast force-enabled Reduce Transparency and the
  transparency checkbox could not be uncleared while contrast was on (user-verified 2026-08-29), so
  the coupled state was the **only** reachable increased-contrast state and the 26.5 profile carries
  a caveat saying its fixtures were captured in it. On 27 all seven increased-contrast runs attested
  `increaseContrast=1` with `reduceTransparency=0`, and the harness — which records the coupling as
  a profile caveat whenever it observes it — wrote **no coupling note in any of the 56 run
  manifests**. So the 27 increased-contrast bed is a *different state* from the 26.5 bed of the same
  name, and a difference between the two on that profile is confounded with the decoupling until
  they are separated. Recorded as a caveat on the two 27 accessibility profile entries, **beside the
  26.5 caveat and never over it**; the evidence under it is an attestation, not a note. Whether the
  coupling's disappearance is itself a change G2 should read is a question for G2's charter.
- **The backdrops did not move across the OS change** (2026-09-19, G1 Part B). All 32 background ids
  the 27 runs composited over are byte-identical to the rasters the 26.5 bundle indexes — 896
  comparisons, zero disagreements. The harness draws them with its own CoreGraphics generators and
  nothing guaranteed 27 would rasterise them identically; had they moved, `materialize` would have
  refused the publication rather than filing cells under a backdrop they were not drawn on. G2
  therefore reads 27 against 26.5 over the same backdrop bytes on both sides.
- **The 27 bed is five cells LARGER than the 26.5 bed** (2026-09-19, G1 Part B). Clause 2 asks for a
  shortfall named cell by cell and there is none: every profile filed exactly what it declared, and
  the five cells 26.5 declared but never published were all captured on 27 — including
  `light-solid__capsule-button__inactive` on both dark profiles, which claims §5.148 §1 found the
  26.5 publishing run passing over. A 27 cell with no 26.5 counterpart is one G2 reports rather than
  diffs.
- **A whole-file hash of the shared manifest could not survive a second bed** (2026-09-19, G1 Part B;
  §5.150 Part B §8). `freeze.py` hashed `fixtures/manifest.json` as one file, which was right while
  the bundle held one bed and became unable to say anything useful the moment the 27 profiles'
  entries went into it — it can only report "the 26.5 bed moved" for a change that added a bed beside
  it. It now hashes the manifest per unit, exactly as it already hashed the matrix per 26.5 row. The
  superseded whole-file reading is recorded, and the amendment is proved against the pre-publication
  snapshot three ways before it was adopted. **The general lesson for X1: a freeze over a file two
  beds share has to be a freeze over the units of that file, not over its bytes.**
- **`materialize` could not publish a profile the bed had never held** (2026-09-19, G1 Part B). On
  the new-key path it copied every PNG in and skipped the manifest silently — fixtures on disk the
  record does not describe. Unreachable until this wave, because every prior publication appended to
  a profile the bundle already declared. Fixed with the entry built from the runs' own headers and a
  refusal when they disagree.
- **The 27 material is not SDK-gated, on pixels: the two bundles produce identical bytes**

  audit of the parent's banked runs). It attested 3 of 8 cells: five recorded

- **The harness cannot be narrowed to one profile, and with two beds declared that costs the
  sitting twice over** (2026-09-18, G1 (1); §5.150 §2, tracker). `main.swift` selects profiles by

- **Show Borders is `ButtonShapesEnabled` in `com.apple.Accessibility`** (2026-09-18, Decision Log

- **The slider is a material parameter, not a policy.** `NSGlassTintAmount`'s value appears
  unrounded as the glass filter's `inputBlurFillNormalOpacity`, and the face fill's alpha follows a

- **`LC_BUILD_VERSION`'s `sdk` field does not record the SDK a `build.sh` bundle compiled against.**
